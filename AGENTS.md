# Harbor Jam — Guide for Future Development

This file is written for whoever continues this project — a human developer or an AI coding agent. Read it before changing anything. It explains the invariants that must never break, how the pieces fit, and the safe recipes for the most likely kinds of work: new levels, new mechanics, new UI, and scaling up.

## 1. Non-negotiable design invariants

These come from the original design brief. **Do not violate them, even if a change seems fun:**

1. **Zero pressure.** No timers, move limits, lives, scores, stars, move counters, or fail states — anywhere, ever. A wrong tap costs nothing: bump + soft horn only.
2. **Unlimited undo.** The undo stack (`game.departed`) must always restore any departed ship, all the way back to level start. Any new mechanic must be undo-compatible or ambient (like patrols, which are time-driven and need no undo state).
3. **Depth from layout, not stress.** Difficulty may come only from geometry and (in The Strait) timing windows that reopen forever. Patrol warships never punish — a denied tap is a no-op with feedback.
4. **Calm aesthetic.** Muted palettes, soft shapes, gentle motion and audio. No aggressive colors, flashing, or urgency cues.
5. **No build step.** Vanilla ES modules, no frameworks, no bundler, no external assets (all graphics are canvas vectors, all audio is Web Audio synthesis). It must run from any static file server.

## 2. Architecture map

```
main.js ──► owns the rAF loop and input; wires everything
   │   game.updatePatrols(dt) each frame; recomputes hover status each frame
   ▼
game.js ──► PURE logic, no DOM (importable from Node — the generator does this)
   │        Game class: ships Map, occ Map (cell→shipId), departed stack, patrols
   │        departStatus(ship) → 'clear' | 'blocked' | 'patrol'
   │        exports departure kinematics: departureTiles/Duration/TimeAt
   ▼
renderer.js ► ALL drawing + animation state (departures, nudges, gulls, hover)
              THEMES live here; Renderer reads Game but never mutates it
solver.js ──► fixpoint solvability check + level validation (dev tool + load-time check)
levels.js ──► AUTO-GENERATED by tools/generate-levels.mjs. Never hand-edit.
audio.js ───► AudioEngine; lazily initialized on first user gesture (browser rule)
ui.js ──────► DOM menus/HUD + localStorage (key: 'harborjam.v1')
```

Data flow for a tap: `main.js pointerdown → game.tryDepart(id)` → if departed, `renderer.startDeparture(ship)` + horn; if `'patrol'`, nudge + `audio.denied()` + alert ring; if `'blocked'`, nudge + blocked horn. **Game state changes synchronously; animation is presentation only.** Undo mid-animation works because `renderer.cancelDeparture(id)` just drops the animation.

## 3. Critical couplings (easy to break silently)

- **Departure kinematics are a contract.** `game.js` exports `departureTiles(laneLen, shipLen)`, `departureDuration(tiles)`, `departureTimeAt(dist, tiles)`. The renderer animates with them AND `interceptingPatrol()` predicts warship collisions with them. If you change animation speed/easing, change it in `game.js` only, and re-check that ease-in inversion (`t = dur·√(d/tiles)`) still matches the easing used in `renderer.drawDepartures` (`dist = p² · tiles`).
- **Ship coordinate convention:** `(x, y)` is the **top-left-most** occupied cell. E/W ships extend along +x, N/S along +y; `direction` only says which end is the bow (`bowCell()`). All of game.js, solver.js, renderer.js, and the generator assume this.
- **Patrol lines must stay clear of static content.** The generator forbids it; `solver.validateLevel` errors on it. If you add hand-authored levels with patrols, keep every cell of the patrol's row/column free of ships and obstacles.
- **The solver's fixpoint shortcut is only valid while departures free space monotonically.** If you ever add a mechanic where a move can *block* something (moving obstacles that toggle, ships that rotate, one-way gates), the fixpoint argument dies — you must replace `solveLevel` with a real BFS/DFS over states. Check this before adding any new mechanic.
- **Generator determinism:** each level's RNG seed is `0xB0A7 + index * 101`. Existing levels keep their exact layouts only if their `SPECS` entry and index are unchanged. **Append** new specs; never reorder or insert in the middle (players' `completed[]` progress is index-based too).

## 4. Recipe: adding or rebalancing levels

1. Edit the `SPECS` table (and `NAMES`) in `tools/generate-levels.mjs`. Knobs: grid size, ship count, obstacle count, `tier` (length-mix weights), and `guards` for patrol levels (`edge: N/S/E/W`, `length`, `speed` in tiles/sec).
2. Run `node tools/generate-levels.mjs`. It prints a stats table — **waves** (dependency depth, higher = deeper puzzle) and **openers** (initially movable ships, lower = harder to read).
3. If you add levels beyond 40, add a new `.level-section` header in `ui.js refreshLevelSelect` if they form a new chapter, and consider new `THEME_UNLOCK` thresholds in `ui.js`.
4. Hand-authored levels are fine too: append the JSON object to the generated array pattern in a *separate* module and concatenate, or add a `HANDMADE` list the generator appends — but always ensure `solveLevel(def).solvable` passes. The page logs `console.warn` for any unsolvable level at load.

## 5. Recipe: adding a new mechanic

Follow the patrol-warship pattern — it's the template for "ambient, undo-free" mechanics:

1. Define it in level JSON (extend the generator to emit it).
2. Parse it in `Game.loadLevel`; update per-frame state in a method main.js calls from the loop (like `updatePatrols`).
3. Extend `departStatus()` with a new status string if it can deny departures; return the blocking entity for feedback.
4. Add rendering in `renderer.js` (new draw method called from `render()`), a sound in `audio.js`, and a hover-lane color in `THEMES` + `drawHoverLane` if it creates a new deny reason.
5. Add validation to `solver.validateLevel`, and decide explicitly: does this mechanic affect *solvability* or only *timing*? (See the fixpoint warning above.)
6. Add a one-line `ui.showHint(...)` in `startLevel` for the first levels that use it.

## 6. Recipe: UI / visual changes

- HUD and menus are plain DOM in `index.html` + `styles.css`; the board is one canvas. Prefer DOM for chrome (buttons, overlays) and canvas for anything in the water.
- Themes: each theme in `renderer.js THEMES` is a flat palette object. To add a theme: add the object, add a `body.theme-<key>` block in `styles.css` (page background + overlay tints), add its unlock threshold to `THEME_UNLOCK` in `ui.js`. Everything else picks it up.
- The canvas is DPR-aware (capped at 2×). All drawing happens in CSS-pixel space via `ctx.setTransform(dpr, ...)`. Layout = `renderer.layout()`: tile size clamped 12–70px, board centered. Hit-testing goes through `renderer.cellAt(px, py)`.
- Mobile: `pointerdown` for taps (works for touch + mouse); hover preview is desktop-only (`pointerType === 'mouse'`). Keep hit targets tile-sized; the HUD hides text labels under 520px (`.lvl-name`, `.btn-txt`).
- Performance budget: 60fps with 40 ships + 4 patrols. Per-frame allocations in `render()` are mostly avoided; keep it that way (no `Array.from`/spreads/closures in the draw loop; reuse objects; splice-in-place for particle pools). `ctx.roundRect` is used — supported everywhere modern; polyfill only if you must target 2021 browsers.
- Audio: everything is synthesized in `audio.js`. New sounds follow the pattern: oscillators/noise → filter → gain envelope → `this.master`. The AudioContext starts on first user gesture (`document pointerdown → audio.init()`), and mute just zeroes the master gain (sounds keep "playing" silently — cheap and glitch-free).

## 7. Testing & verification

- **Logic:** `window.__harborjam` (defined in `main.js`) exposes `{ game, renderer, startLevel, solveLevel, LEVELS, currentLevel }`. Automated playthroughs: `startLevel(i)`, then tap in `solveLevel(LEVELS[i]).order` order by dispatching `PointerEvent('pointerdown')` at `renderer.cellCenter(ship.x, ship.y)` offset by the canvas bounding rect. Patrol cases: set `game.patrols[0].pos/.dir` directly to force `'patrol'` vs `'clear'` and assert `departStatus`.
- **Levels:** `node tools/generate-levels.mjs` must print all levels; the page must load with zero `console.warn`.
- **Visual:** check one Open Harbor level, one Strait level (warship + amber hover), the level-select, and a ~375px viewport (HUD must not overflow — this regressed once).
- Acceptance basics that must keep passing: blocked tap changes nothing; undo restores to level start; progress survives refresh; all levels solvable; touch + mouse both work.

## 8. Scaling ideas that fit the design (pre-vetted)

- **More chapters:** new 20-level sections with one new ambient mechanic each (drifting fog banks that hide-but-don't-block, tide cycles that open/close a shallow row on a slow rhythm, ferries crossing mid-board). All fit the patrol template — timing, not punishment.
- **Daily harbor:** seed the generator with the date (`YYYYMMDD` as seed), one fresh level a day. The generator is already deterministic-by-seed; expose `generate(spec, rng)` from a shared module rather than duplicating it.
- **Level editor:** the JSON format is human-writable; a palette-and-paint canvas editor writing that JSON + a live `solveLevel` check is a weekend feature.
- **PWA/offline:** add a manifest + tiny service worker; there are zero external requests, so caching is trivial.
- If the project grows beyond ~10 modules, adding a bundler is acceptable **only** if `npx serve` on the raw source keeps working (e.g., keep ES modules valid) — the no-build-step property is part of the design.

## 9. Known quirks

- `levels.js` is generated — regenerate, don't edit (a header comment says the same).
- The first 20 levels' layouts are frozen by seed; players may have muscle memory. Treat published level layouts as immutable content.
- `Game.restart()` calls `loadLevel(this.def)`, which re-parses patrols — patrol positions reset to `startPos` on restart. Intentional.
- Fleet-boat SVGs in `ui.js boatSvg()` are decorative doubled-path silhouettes; if you touch them, just redraw them cleanly.
- The completion overlay waits 950 ms (`completeTimer`) so the last wake fades first; `cancelCompleteTimer()` guards every path that leaves the level. Keep that guard if you add new navigation paths.
